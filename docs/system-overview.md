# 自研 LLM + VLM 短视频批量剪辑系统设计稿

## 1. 系统定位

本项目不是通用视频编辑器，也不是让大模型直接对原始视频做端到端剪辑的系统。

本项目的定位是：

- 面向短视频信息流场景的素材库驱动型批量剪辑系统
- 以人工清洗后的可复用 `shot` 为基础资产
- 以 VLM、ASR、结构化标签和向量索引为素材理解基础
- 以 LLM 负责文案生成、镜头编排和装配决策
- 以批量生成多条可控视频变体为输出目标

一句话概括：

> 这是一个“基于素材库语义索引的短视频自动编排系统”，而不是一个“让大模型直接剪视频的系统”。

## 2. 基本处理流程

系统的核心流程如下：

1. 人工对原始素材进行预处理和清洗
2. 将原始素材裁成单个可复用的干净 `shot`
3. 按产品对素材归类，并维护产品卖点信息
4. 对素材执行自动分析
5. 生成标签、描述、转写文本和结构化元数据
6. 将素材信息向量化并写入索引
7. 用户选择产品后生成文案
8. 将文案生成或录制为最终口播/旁白配音
9. 基于配音时间轴和素材库约束进行镜头编排
10. 生成可执行时间线并完成画面剪辑
11. 根据最终时间线音频识别或对齐字幕
12. 加入 BGM，并调整 BGM 与配音的混音关系
13. 输出成片

需要强调的是，批量剪辑不是按素材库内容原封不动拼接，而是基于编排结果对素材做进一步裁切、截取和装配。

对于信息流短视频，文案就是最终口播或旁白的配音文本。系统的主时间轴应由配音生成后的真实音频时间轴驱动，画面剪辑围绕该音频时间轴展开。

## 3. 素材资产定义

### 3.1 清洗后的 `shot`

系统使用的基础素材单元不是原始视频，而是人工清洗后的干净 `shot`。

当前约定：

- 去掉前后无用内容，例如打板、空镜、失误片段、内标注剪辑点
- 每个 `shot` 应为单个可复用的稳定片段
- 一个 `shot` 尽量只表达一个主要内容，避免一个片段内出现多个明显语义跳变

人工预处理是整个系统质量上限的前提。

### 3.2 素材类型

当前素材主要分为两类：

- `visual_only`
  - 没有人物语音的纯画面素材
- `talking_head`
  - 有人物语音配音的口播录制素材

素材类型需要在预处理阶段明确标注。

### 3.3 口播素材的句段化

对于 `talking_head` 类型素材，除了保留 `shot` 本身，还需要保留带时间轴的语音转写信息，例如：

```text
[00:00:03:00]-[00:00:05:00] 大家好
```

在系统设计上，口播素材会从单个素材对象中解析出多个可检索的语音句段。

当前确认的对象划分为：

- `shot`
- `speech_segment`

其中：

- `shot` 是素材库中的基础复用单元
- `speech_segment` 是从口播素材内部拆分出的可检索语义单元

后续检索与编排应优先使用句段级对象，而不是整条口播素材。

## 4. 产品与卖点建模

素材库按产品组织是整个系统的基础前提。

每个产品至少应具备：

- 产品基础信息
- 产品卖点信息
- 与产品关联的素材集合

同时需要强调：

- 卖点不能只挂在产品上
- 素材本身也要标记其能够承载的卖点

建议每个素材或口播句段都允许标注：

- `primary_selling_point`
- `secondary_selling_points`

这样系统才能把“卖点表达”和“镜头选择”关联起来。

## 5. 系统分层设计

### 5.1 素材预处理层

补充约束：

- 客户端必须存在独立的“预处理工作区”，用于承接原始视频选择、裁切和人工标注
- 原始视频、处理中间态、仅保存未提交的 clean shot 都不进入服务端素材库
- 服务端只识别正式素材库对象，不识别客户端待处理工作区对象
- 未入库对象对服务端不可见，服务端不得直接读取、分析、调度或创建素材处理任务
- 唯一例外是客户端主动发起的预处理 ASR 推理：`local-agent` 仅上传当前 I/O 选区导出的临时音频和时间轴上下文到服务端 FunASR，服务端不得访问工作区原始视频
- ASR 临时音频仅用于本次推理，结果直接返回本地工作区；服务端不得为其创建 `asset`、素材处理任务、检索记录或素材库预览，推理完成后必须删除临时文件
- 用户在预处理窗口核对和修改转写草稿；只有正式提交时，确认后的转写文本才随 clean shot 进入服务端素材库
- 用户可以从待处理视频列表打开任意一条进入预处理窗口，而不是要求逐条返回列表处理
- 预处理窗口内部应支持“上一条 / 下一条”切换，便于连续处理批量素材
- 用户可以执行“仅保存，不提交入库”，此时结果只保留在本地预处理工作区
- 只有用户明确执行“提交入库”后，clean shot 才成为服务端正式 `asset`

建议预处理工作区采用明确状态流：

```text
待处理 -> 本地已保存 -> 待提交 -> 已入库
```

状态语义约束：

- `待处理`：原始视频已进入本地工作区，但尚未形成可提交的 clean shot 结果
- `本地已保存`：用户已经保存当前预处理结果，但结果仍只存在本地，不进入服务端素材库
- `待提交`：当前素材已经在客户端工作区完成全部预处理与分析，包括人工处理、`ffprobe`、抽帧、VLM 以及必要的转写补充，但尚未正式提交入库
- `已入库`：用户已执行提交，服务端已创建正式 `asset`
- 预处理工作区整体应支持“清空”
- “清空”作用于整个本地预处理工作区，可清空其中的 `待处理`、`本地已保存`、`待提交` 以及本地保留的 `已入库` 记录
- “清空”后的本地工作区应回到空工作区状态，由用户重新选择或导入原始视频
- “清空”只删除本地工作区记录与本地文件，不应影响已经 `已入库` 的服务端正式资产

职责：

- 接收人工清洗后的素材
- 将素材标准化为可复用的 `shot`
- 记录人工标签和素材类型

该层输出的是标准化资产记录。

### 5.2 素材理解层

职责：

- 提取基础媒体信息
- 对素材进行视觉理解
- 对口播素材进行转写和时间轴对齐
- 输出结构化标签和开放语义描述

建议处理链路：

- `ffprobe`
  - 提取时长、分辨率、帧率、编码等信息
- VLM 抽帧分析
  - 分析画面内容、景别、运镜、产品出现情况
  - 当前标准输入固定为 clean shot 的 `10%` / `50%` / `90%` 三帧
- ASR
  - 服务端部署 FunASR，由客户端上传当前 I/O 选区的临时音频，对 `talking_head` 生成带时间轴的转写草稿
  - 推理结果回填本地工作区，供用户核对和修改；不生成 SRT 文件，不直接写入素材库
- 融合规则
  - 合并人工标注、VLM 和 ASR 结果

执行时机与边界约束：

- `ffprobe`、抽帧和 VLM 分析应在正式提交入库之前完成
- 这些处理属于客户端预处理工作区链路，而不是服务端素材库链路
- 未入库前，服务端不得对该对象执行任何素材分析或处理；仅允许客户端显式上传当前选区临时音频，调用无状态 FunASR 推理
- FunASR 推理不以未入库对象为输入标识，不进入服务端任务队列，不写入素材库、检索索引或素材级日志；临时文件在推理结束后删除
- 未入库前，服务端也不应对该对象提供素材级预览、素材级查询结果或后台任务编排能力
- 未入库前，服务端不允许把该对象当作“可操作素材”看待；无论是分析、检索、预览、调度还是任务引用，前提都必须是它已经正式入库
- 进入 `待提交` 状态的前提之一，是这些处理已经完成
- 正式提交动作本身负责把已经处理完成的 clean shot 和元数据写入服务端正式素材库

### 5.3 检索与索引层

职责：

- 为编排阶段提供高质量素材召回能力
- 同时支持结构化过滤和语义检索

建议采用双索引：

- 结构化索引
  - 用于按产品、时长、素材类型、景别、是否口播等条件做过滤
- 向量索引
  - 用于按语义召回相关 `shot` 或口播句段

建议的索引粒度：

- `shot` 级索引
- `speech_segment` 级索引，仅针对口播素材

关于业务标签补充，还应明确区分两类素材策略：

- 海量普通素材不依赖人工逐条建立强卖点映射，主路径仍然依赖结构化标签、开放语义描述和向量召回
- 高价值精选素材允许人工补充更强的业务标签，作为额外增强层，而不是海量素材的基础入库门槛
- 这类增强标签建议仅作用于正式 `asset`，不作用于未入库的本地工作区对象

### 5.4 生成与编排层

职责：

- 根据产品、卖点、风格和时长约束生成文案
- 将文案生成或录制为最终口播/旁白配音
- 根据配音时间轴规划镜头结构
- 在素材库中检索并装配合适的素材片段
- 产出可执行的时间线方案

建议拆分为三个逻辑步骤：

1. 文案生成
2. 配音生成与时间轴解析
3. 分镜规划
4. 素材匹配与时间线装配

### 5.5 配音与渲染运行环境

服务端以独立容器承载耗时媒体运行环境，业务服务通过 Docker 内部网络调用：

- `tts`
  - 运行 CosyVoice3，模型缓存使用持久 Docker volume
  - 提供参考音频驱动的合成能力，不暴露给浏览器
  - 配音文件、真实时长和后续 `narration_segments` 仍由业务服务负责保存和管理
- `renderer`
  - 运行 Remotion、Chromium 和 FFmpeg
  - 当前仅作为运行环境与最小 smoke render 验证，不直接承担业务时间线
  - 后续只接收经过服务端校验的 `edit_plan`，不得直接向客户端暴露任意文件路径或渲染脚本入口

CosyVoice 与 FunASR 共用服务器 GPU；当前部署使用半精度 CosyVoice3 模型。Remotion 默认使用 CPU，避免与模型推理竞争显存。

### 5.6 当前已落地的旁白任务链

音色和正式旁白属于服务端生成对象，不属于 `local-agent` 预处理工作区：

```text
browser -> API -> generation_run / generation_tasks -> worker -> CosyVoice -> WAV -> FunASR -> narration_segments -> candidate retrieval -> edit_plan
```

- 浏览器只能调用受认证的音色、试听和工作台 API；不能调用 `tts` 或 `asr` 容器。
- 参考音频、固定样音、试听 WAV 和正式旁白 WAV 均保存在服务端 `storage/` 下。
- 音色创建或编辑、当前文案试听和正式旁白分别对应异步任务；前端通过状态轮询展示结果，不阻塞文案编辑。
- 正式旁白完成后，FunASR 生成连续且不重叠的 `narration_segments`，它们是后续编排的真实时间轴锚点。
- 每个确认文案对应一个 `generation_run`。该根对象聚合旁白与编排子任务，当前只有 `generating`、`completed` 和 `failed` 三种业务状态。
- worker 根据旁白句段、beat 和产品约束检索候选素材，LLM 只能从候选闭集选择单源连续片段。候选快照、`edit_plan` 与 `clip_segments` 均持久化，供后续渲染器复核和消费。
- 当前编排完成仍属于 `generating / plan_ready`；最终视频尚未渲染，因此成品库不会把仅有旁白或编排的任务标记为“已完成”。

## 6. 标签体系设计

素材标签应同时包含结构化标签和开放语义标签，两者不能互相替代。

### 6.1 结构化标签

适合用于过滤、规则约束和统计：

- 时长
- 分辨率
- 帧率
- 素材类型
- 景别
- 运镜
- 是否有人
- 是否有产品主体
- 是否有语音
- 是否适合作为首镜
- 是否适合作为过渡镜头

### 6.2 开放语义标签

适合用于向量召回和编排理解：

- 画面描述
- 动作描述
- 场景描述
- 情绪描述
- 产品使用场景
- 卖点相关描述
- 片段角色描述，例如开头钩子、卖点展示、CTA 辅助镜头

## 7. 素材理解与索引原则

### 7.1 双表示原则

每个素材对象都应同时具备两种表示：

- 结构化字段表示
- 语义向量表示

结构化字段负责精确过滤，向量表示负责语义召回。

### 7.2 多粒度索引原则

系统不应只对整条素材建索引，还需要对可复用的语义子单元建索引。

至少应支持：

- `shot` 级索引
- `speech_segment` 级索引

### 7.3 卖点映射原则

素材理解结果必须回答两个问题：

- 这个素材画面里有什么
- 这个素材适合表达什么卖点

如果只有视觉描述而没有卖点映射，编排层很难稳定产出可用结果。

## 8. 时间线装配建模

当前已经确认：

- `narration_segment` 是主叙事音频时间轴单元
- `clip_segment` 是画面时间线装配层的最小剪辑单元
- `talking_head` 和 `visual_only` 在时间线层应统一建模
- `clip_segment` 应严格限定为单源连续片段
- `clip_segment` 应携带片段级必要编辑指令，但不承载复杂效果编排

这意味着文案生成后会先形成配音，配音生成后的真实时间轴成为后续画面剪辑的主锚点。无论素材类型如何，进入画面时间线后都应映射为同一类 `clip_segment`，只是在字段使用方式上存在差异。

### 8.1 主叙事音频时间轴

对于信息流短视频，文案就是最终口播或旁白内容。

例如：

```text
我挺喜欢这种省心的小装备。上车它会亮，停车一会儿自己休眠，车一动又自动亮起来，不用每次都手动开关。日常通勤用起来很顺手，也更省电。
```

这段文案生成或录制后的配音内容也应保持为同一段文本。

系统应先得到配音，再基于配音产生的真实时间轴进行画面编排。配音时间轴可以进一步拆分为多个 `narration_segment`，用于承载：

- 对应的文案文本
- 该段音频在最终时间线中的起止时间
- 该段表达的卖点或意图
- 后续画面剪辑的对齐锚点

因此，系统主链路应理解为：

```text
script -> voiceover -> visual edit -> subtitle recognition/alignment -> bgm mix -> final video
```

这里的“单源连续片段”指的是：

- 一个 `clip_segment` 只引用一个来源素材
- 一个 `clip_segment` 只描述该来源素材上的一个连续时间区间

也就是说，复合多个来源的结构不应落在 `clip_segment` 这一层，而应由更高层的时间线装配关系表达。

### 8.2 `clip_segment` 的设计原则

`clip_segment` 的设计目标是：

- 成为时间线里的最小可执行片段
- 表达“从哪个素材的哪一段，被如何放进画面时间线”
- 保持足够简单，便于检索结果装配、LLM 输出和渲染执行

因此，`clip_segment` 应满足以下原则：

- 严格单源
- 严格连续区间
- 可追溯到素材来源
- 可表达基本的时间线放置和片段级播放控制
- 不直接承载复杂视觉特效、复合动画或多源组合结构
- 可选关联到某个 `narration_segment`，用于说明该画面片段服务于哪段配音表达

### 8.3 `clip_segment` 建议承载的信息类型

当前建议 `clip_segment` 至少承载以下几类信息：

- 身份信息
  - 片段自身标识
  - 所属编排方案标识
  - 逻辑顺序标识
- 来源信息
  - 来源素材
  - 来源 `shot`
  - 可选的来源 `speech_segment`
  - 素材类型
- 裁切信息
  - `source_in`
  - `source_out`
- 时间线信息
  - `timeline_in`
  - `timeline_duration`
  - `track_role`
- 基础播放控制
  - `playback_rate`
  - 是否保留原声
  - 是否静音
  - 音量增益
- 叙事关联信息
  - 可选关联的 `narration_segment`
  - 卖点标识
- 轻量装配提示
  - 轻量转场提示
  - 备注信息

### 8.4 字幕与 BGM 的位置

字幕不是编排阶段的核心对象。字幕应在画面剪辑完成后，基于最终时间线中的口播/旁白音频进行识别或强制对齐生成。

BGM 也不是主叙事时间轴。BGM 应作为后置混音层，在画面剪辑和字幕处理之后加入，并根据配音进行音量、淡入淡出和 ducking 等混音调整。

### 8.5 不应放入 `clip_segment` 的内容

当前建议以下内容不要直接放入 `clip_segment`：

- 多源复合片段结构
- 复杂关键帧动画
- 遮罩和合成特效参数
- 复杂调色参数
- 大型模板样式对象
- 完整视觉效果链路
- 字幕识别结果
- BGM 混音策略

这些内容更适合作为更高层的模板规则、效果层或渲染层能力存在，而不是压进最小剪辑单元。

## 9. 生成与编排原则

### 9.1 LLM 的职责边界

LLM 适合负责：

- 文案生成
- 卖点组织
- 视频结构规划
- 基于候选素材结果做编排决策

### 9.2 不应交给 LLM 的职责

不建议让 LLM 直接承担以下任务：

- 直接理解未经处理的原始视频
- 不依赖检索和约束凭空选镜
- 直接生成不可解释的最终时间线

系统应先完成素材结构化，再让 LLM 做高层规划与选择。

### 9.3 编排流程约束

建议的编排流程为：

1. 读取产品和卖点信息
2. 生成文案
3. 根据文案生成或录制配音
4. 解析配音时间轴并形成 `narration_segment`
5. 基于 `narration_segment` 生成分镜规划
6. 检索候选素材
7. 在候选素材中装配画面镜头
8. 输出时间线数据

LLM 的输入应是受控素材集合，而不是无限上下文中的原始素材库。

## 10. 批量剪辑的设计关注点

本系统的目标包含批量生成，因此设计上需要考虑重复控制和多样性控制。

主要关注点包括：

- 文案重复
- 开头镜头重复
- 常用素材被过度复用
- 成片结构过于单一

因此系统设计中应预留以下控制能力：

- 文案去重策略
- 首镜去重策略
- `shot` 使用频次惩罚
- 模板或结构多样性控制

## 11. 核心数据对象

当前建议的核心数据对象包括：

- `products`
- `product_selling_points`
- `assets`
- `asset_analysis`
- `speech_segments`
- `embeddings`
- `generation_tasks`
- `script_variants`
- `narration_segments`
- `edit_plans`
- `render_jobs`

### 11.1 `assets`

建议至少包含：

- `id`
- `product_id`
- `file_path`
- `source_type`
- `duration_ms`
- `width`
- `height`
- `fps`
- `manual_clean_status`

### 11.2 `asset_analysis`

建议至少包含：

- `scene_description`
- `shot_size`
- `camera_motion`
- `contains_person`
- `contains_product`
- `visual_tags`
- `selling_point_tags`
- `quality_score`

### 11.3 `speech_segments`

建议至少包含：

- `asset_id`
- `start_ms`
- `end_ms`
- `text`
- `speaker_style`
- `emotion`
- `keywords`

### 11.4 `narration_segments`

建议至少包含：

- `script_variant_id`
- `text`
- `audio_asset_id`
- `timeline_in_ms`
- `timeline_out_ms`
- `selling_point_id`
- `intent`

## 12. 设计结论

当前形成的系统设计共识如下：

- 系统核心是素材库驱动的自动编排，而不是通用编辑器
- 批量剪辑不是原封不动拼接素材，而是基于编排结果进行二次裁切与装配
- 高质量人工预处理是系统成立的前提
- 客户端必须具备独立的本地预处理工作区
- 原始视频、处理中间态和“仅保存未提交”的结果不进入服务端素材库
- 服务端只认正式素材库，不处理待处理工作区中的任何未入库对象；唯一例外是客户端上传临时音频的无状态 FunASR 推理
- 未入库对象不能被服务端当作素材处理；FunASR 结果只回填本地转写草稿，服务端只在“明确提交入库”时接收 clean shot 和确认后的元数据
- 用户可以打开任意待处理视频进入预处理窗口，并在窗口内切换上一条 / 下一条
- 只有明确提交后的 clean shot 才进入服务端并创建正式 `asset`
- `待提交` 的定义是全部预处理和分析完成，但尚未正式提交入库
- 结构化标签和向量索引必须同时存在
- 口播素材会从单个素材对象中解析出多个可检索的 `speech_segment`
- `shot` 是素材库中的基础复用单元
- `speech_segment` 是口播素材的语义检索单元
- 文案就是最终口播或旁白的配音文本
- `narration_segment` 是主叙事音频时间轴单元
- 画面剪辑应围绕配音时间轴展开
- 字幕应在画面剪辑完成后，基于最终时间线音频识别或对齐生成
- BGM 是后置混音层，应在配音和画面剪辑确定后加入
- `clip_segment` 是画面时间线装配层的最小剪辑单元
- `talking_head` 和 `visual_only` 在时间线层应统一建模
- `clip_segment` 应严格限定为单源连续片段
- `clip_segment` 应承载必要的片段级编辑指令，但不承载复杂效果系统
- 卖点不仅属于产品，也必须映射到素材
- VLM 当前固定使用 clean shot 的前中后三帧，即 `10%` / `50%` / `90%`
- LLM 应负责规划与编排，不应替代素材理解与底层剪辑逻辑
- 批量系统必须从设计上考虑多样性控制和重复控制
