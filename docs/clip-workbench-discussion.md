# 剪辑任务工作台讨论

本文记录“剪辑任务工作台”当前的产品和架构讨论结论，用于后续逐步拆分实施任务。

本文不是实施任务清单。已经确认并进入开发的事项，应再同步到 [docs/task/phase-3.md](./task/phase-3.md)。

## 1. 目标

工作台是系统的主要生产入口。用户在此选择产品、组织卖点、生成并确认口播文案，然后启动服务端任务完成配音、素材召回和自动编排。

工作台不替代：

- 产品管理：维护长期有效的产品和卖点。
- 素材库：管理已正式入库、可供编排使用的 clean shot。
- 预处理工作区：处理尚未入库的本地视频，服务端任务不得读取其中的素材。

`generation_tasks`、队列和执行日志保留在服务端，用于阶段恢复、失败诊断和审计，但不作为普通用户的页面或主操作路径。

用户导航顺序固定为：

```text
工作台 | 成品库 | 产品 | 预处理 | 素材库 | 设置
```

登录后的默认页面为工作台。普通用户导航不显示“任务”。

## 2. 用户流程

```text
选择产品
-> 选择已有卖点并补充本次自定义卖点
-> 输入文案条数
-> 生成文案 variants
-> 编辑、删除或确认文案
-> 选择确认版本并开始任务
-> 服务端配音、解析主叙事时间轴、召回素材、生成 edit_plan
-> 工作台查看进行中的作品状态
-> 成品自动进入成品库
-> 用户预览、筛选和正式提交成品
```

### 2.1 工作台输入

首期输入保持克制：

- 产品：必填，作为素材范围和产品事实的根约束。
- 已有卖点：从该产品的卖点中多选，可移除。
- 自定义卖点：允许用户追加本次任务专用文本。
- 文案条数：生成的 script variant 数量。

自定义卖点默认只写入本次生成任务的输入快照，不自动写回产品管理。后续可单独提供“保存为产品卖点”操作，避免临时要求污染长期产品资料。

目标时长、风格、受众、平台和是否启用口播素材等约束有价值，但不是首期工作台必填项；确定首期文案质量后再逐项增加。

### 2.2 文案生成与人工确认

点击“生成文案”后，服务端 LLM 应使用严格 JSON 输出多个 variants。每个 variant 至少包含：

- `script_text`：可直接作为最终口播或旁白的文本。
- `hook`：开头表达角度或钩子。
- `estimated_duration_ms`：文案长度推导的粗略预计时长，不得替代真实配音时长。
- `editing_intent`：初步编排意图。
- `beats`：按表达节奏拆分的卖点、画面目标、建议素材类型和叙事作用。

`editing_intent` 和 `beats` 是创意分镜说明，不是最终 `edit_plan`。在此阶段不得输出具体 `asset_id`、素材 I/O、最终时间线或渲染参数。

首期用户可以逐条修改文案并将版本标记为确认或不采用；初步编排意图作为只读的创意说明展示。开始任务时只启动被用户确认且选中的版本，避免把所有生成文案无差别投入后续生产。

用户编辑 `script_text` 后，初步编排意图会失效，正式任务必须基于最终确认的文案重新计算意图和实际编排。

### 2.3 成品库

成品库与素材库是两个不同的业务对象：

- 素材库存放可复用的 clean shot。
- 成品库存放任务产生的最终视频输出。

成品库以视频预览为主体的瀑布流卡片呈现。卡片显示产品、文案钩子、时长、生成时间和生成状态；生成中的卡片显示当前阶段和进度，已完成的卡片提供成品预览。

用户在工作台点击开始任务后，成品立即以 `generating` 进入成品库，完成后转为 `completed`。成品库不承接待提交或已提交状态，也不承担任务日志职责。未来的业务提交属于独立动作，不改变视频生成状态。用户不需要面对任务 ID、队列日志或内部阶段对象，但成品必须保留对生成任务、文案版本和编排方案的追溯关系。

## 3. 正式任务链

确认文案后的生产任务采用阶段化链路：

```text
script variant confirmed
-> TTS voiceover
-> ASR / forced alignment
-> narration_segments
-> shot requirement generation
-> vector retrieval and structured filtering
-> LLM candidate-grounded planning
-> edit_plan validation
-> future render
```

### 3.1 主时间轴原则

信息流视频的主时间轴必须来自最终配音的真实音频时长。不能以字符数或 LLM 估算时长直接生成最终镜头时间线。

因此，文案确认后可以先生成创意意图，但实际 `clip_segment` 装配必须等待：

1. 配音文件生成完成。
2. 配音按句段或更细粒度完成时间对齐。
3. `narration_segments` 的时间范围通过连续性校验。

### 3.2 素材选择原则

编排 LLM 不能直接扫描全量素材库，也不能凭空生成素材引用。服务端需要先根据产品、卖点、旁白句段和镜头需求构建受控候选集，LLM 只能在候选 ID 中选择。

候选集的默认边界：

- 仅使用已正式入库的素材。
- 默认按 `product_id` 严格过滤。
- 结合素材类型、时长、景别、运镜、质量和卖点标签进行结构化过滤。
- 再用向量语义召回和重排得到有限候选集。

最终 `clip_segment` 必须保持单源、连续区间，并可追溯到素材和可选的 `speech_segment` / `narration_segment`。

## 4. 数据与状态设计

建议复用 `generation_tasks` 作为生产任务根对象，并补足脚本文案和阶段产物，而不是仅将其作为简单日志记录。

任务至少保存以下快照：

- 产品快照。
- 已选择卖点和自定义卖点。
- 确认的 script variants。
- LLM、TTS、向量模型和提示词版本。
- 任务创建时间的关键运行配置。

建议状态流转：

```text
draft
-> scripts_ready
-> scripts_confirmed
-> queued
-> voicing
-> aligning
-> retrieving
-> planning
-> plan_ready
-> future rendering
-> completed | failed | cancelled
```

阶段失败应记录到任务详情，并允许从最近一个有效阶段重试；不能因一次渲染或模型调用失败而丢失已经确认的脚本和配音结果。

建议新增或落地以下正式对象：

- `script_variants`
- `voiceovers`
- `narration_segments`
- `edit_plans`
- `clip_segments`
- 后续的 `render_jobs`

## 5. 当前代码基线与缺口

当前项目具备产品、卖点、正式素材库、VLM 分析、ASR 句段、向量写入和服务端任务基础。

当前已完成前端原型：

- 已新增 `#/workbench` 和 `#/finished` 路由，工作台为默认首页。
- 已将工作台和成品库置于导航最前，普通用户导航移除了任务入口。
- 产品和已有卖点读取现有真实接口。
- 文案 variants、执行进度和成品状态暂由集中式浏览器 prototype adapter 驱动，并持久化到浏览器本地存储。
- 工作台支持自定义卖点、生成/编辑/确认文案、开始 mock 任务和进行中状态。
- 成品库支持瀑布流预览，以及生成中/已完成筛选；工作台启动的 mock 任务会立即出现在成品库。

尚未具备完整工作台链路，主要缺口如下：

- 当前任务服务只支持测试和素材处理任务，尚无文案、配音、编排任务 API 或 worker。
- `modelgateway` 当前提供素材分析和向量能力，尚无独立的脚本文案生成或编排规划接口。
- 向量已可写入，但 `AssetRepository.SearchByEmbedding` 仍返回“未实现”，尚不能进行实际候选召回。
- `generation_tasks` 数据库结构已有 `variant_count`、目标时长、风格和配置快照等基础字段，但现有服务层未将其用于生产任务创建。
- 尚无 `script_variants`、`voiceovers`、`narration_segments`、`edit_plans` 和 `clip_segments` 的实际持久化与验证链路。

## 6. CosyVoice3

CosyVoice3 是完整生产任务链的前置能力之一，而不是文案工作台本身的前置能力。

建议接入方式：

- 作为服务端独立 `tts` 服务，使用 Docker 内部网络访问，不在 local-agent 执行。
- 提供明确的 TTS 抽象接口，避免业务代码直接依赖 CosyVoice HTTP 细节。
- 配音文件写入服务端存储，并保存 provider、model、voice、采样率、时长和生成参数。
- TTS 生成后复用 FunASR 或强制对齐链路生成句段时间轴，不假设 TTS 服务天然返回可用的字幕时间戳。
- 部署前确认服务器 GPU、模型下载体积、持久化模型缓存、健康检查、超时和失败恢复策略。

在 TTS 未配置时，工作台可以完成文案生成与确认，但不应伪造最终 `edit_plan` 或以预计时长替代真实配音时间轴。

## 7. Remotion 与渲染

Remotion 不属于首期工作台、文案或编排链路的前置依赖。

`edit_plan` 必须保持渲染器无关。首个 renderer 可以基于 FFmpeg 完成基础的素材裁切、顺序拼接、音画对齐、字幕烧录和混音。Remotion 更适合作为后续的渲染适配器，用于品牌动效、模板化视觉层和复杂动态字幕。

不得将 Remotion 组件参数、复杂动画或模板私有结构直接写入 `clip_segments`。

## 8. 推荐实施顺序

### 第一步：工作台文案阶段

- 先完成前端 prototype：使用真实产品和卖点数据，通过集中 mock adapter 验证工作台和成品库交互。
- 前端 prototype 稳定后，再以同一类型和调用边界替换为服务端 API；不得把 mock 数据散落在页面组件中。
- 新增任务草稿和 `script_variants` 持久化。
- 接入独立 Script Generator，生成并校验 JSON 文案与初步编排意图。
- 支持逐条编辑、确认、弃用和选择启动版本。
- 工作台只承接创建和确认文案；成品库承接生成中的作品、完成后的预览和后续独立业务动作。

### 第二步：真实候选检索

- 实现 pgvector 相似度检索。
- 建立镜头需求对象、结构化过滤和候选集重排。
- 保证编排 LLM 只能从候选集选择素材。

### 第三步：CosyVoice3 与 narration 时间轴

- 部署并接入服务端 TTS。
- 保存配音音频与真实时长。
- 通过 ASR / 对齐生成 `narration_segments`。

### 第四步：编排与 edit_plan

- 按 narration segments 生成镜头需求。
- 调用候选集检索和 LLM 编排。
- 生成并校验 `edit_plan` 与 `clip_segments`。

### 第五步：渲染

- 实现基础 FFmpeg renderer。
- 后续按模板和动效需求评估 Remotion。

## 9. 待确认项

- 首期生成多条文案后，是否允许用户只选择其中部分确认版本开始任务。建议允许。
- 首期是否需要目标时长、风格和平台等参数，还是先仅提供产品、卖点和条数。建议后者。
- 首期“开始任务”是否必须同时包含 TTS 和实际编排。建议在 CosyVoice3 和候选检索就绪后再开放完整生产任务；此前只完成文案确认阶段。
